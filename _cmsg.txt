v3.0.2 (手机版 iOS m3): 相册取图、快捷指令修复、手机版剪贴板监听、内置题库装载

【用户报的三个问题】
① 图片识别搜题：点取图框弹出的是「文件」App，找不到刚截的图，没法选图。
② 快捷指令不再搜题，只到「打开软件」那一步。
③ 「开始监听」按钮需要电脑版装 Umi-OCR，手机上能不能改。

【① 图片来源 → 系统相册】
电脑版网页的取图入口是 <div id="imgDrop"> 里藏的
<input type="file" id="imgInput" accept="image/*">（点击 → WKWebView 文件面板
→ 「文件」App）。旧手机版是自己在页面做了 FAB（拍照/相册/剪贴板）走相册；
新版是从**电脑版网页**重建的，电脑版没有 FAB，所以这条口子漏接了。
- 接管 #imgDrop 的点击 → __SB.pickImage()（PHPicker，截屏就在相册里）
- 兜底把 #imgInput.click 置空：同元素上网页的监听注册在先，谁先触发不确定，
  置空后无论顺序如何都只打开相册、且只打开一次
- 补一个「📷 拍照识别」按钮（电脑版页面本身没有相机入口）
- OpenPanelShim.m 的文件类型放宽（原先只放行 image+docx，
  <input accept=".json"> 里根本选不到 json，兜底路径等于死的）

【② 快捷指令：漏了别名】
用户快捷指令用的是 searchbank://fab-clipboard，而 v3.0 首版只认
fab-clip / clip → 落到兜底分支 swapToSearch("") → 只切页、框是空的。
旧版 v2.22 是写了这个别名的，我重写时漏了。现已补全别名：
fab-clipboard / fab-clip / clip / shot / ocr-latest / launch。

【③ 剪贴板监听移植到手机】
网页点「开始监听」会先调 umiBridge.launchGui() 启动 Umi-OCR 桌面程序，
拿到 !ok 就 return —— 手机上连监听都开不起来。
- launchGui 在 iOS 上返回 ok（无需外部程序），让流程走到 startClipboardWatch
- 接管该按钮点击，去掉「启动 Umi-OCR…」「请框选题目」这类电脑版口径提示
- 剪贴板轮询改为 changeCount 门控（见下），并支持**文本与图片**：
  文本 → 交给网页现成的 onClipboardText（它有一套「像不像题干」过滤）
  图片 → 离线识别 + 整页净化 → 直接搜题（复用 v1.0.61 同一条链路）

【关键：iOS 的「允许粘贴」不能踩】
iOS 16 起读取**别人写入**的剪贴板内容会弹一次系统「允许粘贴」。
每 1.2 秒读一次 = 每 1.2 秒弹一次，完全没法用。
新增原生 readClipboardRich：先用 changeCount（读它不碰内容、不弹窗）判断变没变，
没变就直接返回、连内容都不读；真的变了才读一次。
另外用 peek 模式在开启监听时先登记当前内容，避免刚开就把上次复制的旧题目搜一遍。

【剪贴板监听 ↔ 快捷指令 的冲突（用户特意问了）】
两者都会读到同一段文字，不管会搜两遍、还多弹一次「允许粘贴」。
但**不能只按文字去重**：监听走的是网页那套启发式过滤，可能把文字滤掉而没搜；
那时快捷指令若也跳过，就一次都不搜 —— 正好复现问题②。
所以判据用「**真的执行过搜索**」：hook doSearch 记录最近一次实际搜索的文字与时间，
快捷指令侧只有在这个前提下才跳过；并顺手同步监听的游标，
避免监听稍后又把同一段内容当成新内容处理。
测试专门守着这条安全性质：监听把「hi」过滤掉（没搜）后，
快捷指令仍必须照搜。

★ 结论（已与用户确认方向）：**截图请用快捷指令** ——
  按电源键截图是存进相册、**不进剪贴板**，剪贴板监听原理上看不到它；
  快捷指令自己会做 OCR 再把文本放进剪贴板。
  剪贴板监听保留为可选（默认关），给「复制题干文字 / 复制题图」的场景用。

【顺带修掉两个会让用户以为"没反应"的真 bug】
1. 内置题库从来没成功装载过。seedFromBundle 里
   ① `var D = window.DATA` —— 网页是 `let DATA`，顶层 let 进的是全局词法环境，
      **不在 window 上** → 恒为 undefined → 判定直接失败；
   ② `fetch("搜题题库.json")` —— WKWebView 用 file:// 加载页面，
      WebKit 会拦掉 file:// 的 fetch → 内容都取不到。
   改用原生 getBundledBank + 裸标识符访问 DATA。
   （注意不能给 DATA 做 window 别名：网页会 `DATA = mergeData(...)` 整体重赋值。）
2. 冷启动深链搜到残缺库。网页初始化是 `await desktopFS.readData()` 异步把
   沙盒 data.json 读进 DATA，而 localStorage 只有 5MB、装不下 11k 题（8MB）。
   冷启动时深链来得比它早，立刻 doSearch 会搜到残缺库 —— 用户看到的是
   「打开了但没结果」，和「压根没搜」几乎一样难分辨。
   新增「数据就绪」闸门：web 端第一次 readData 完成后（用 setTimeout(0)
   让网页自己的 mergeData 先跑完）放行深链动作，并带 2.5s 兜底。
